# `simply_ip_vault` — API Reference

Exhaustive catalog of every HTTP endpoint this service exposes. Generated by auditing the router
assembly in `src/lib.rs` against every handler under `src/api/`; each entry names the handler that
serves it so a reader can go to the source rather than trust this file.

**Scope:** 33 handler-backed endpoints across 40 route registrations (the difference is aliases,
marked throughout), plus the static-file fallback. Two endpoints are unauthenticated probes; the
remaining 31 sit behind `middleware::auth_middleware`.

**Normative sources.** `RBAC_MODEL.md` governs every authorization rule cited here and overrides this
document where they disagree. `SCHEMA.MD` governs the stored shapes; `AGENT.MD` governs the request
signing scheme reproduced below.

## 1. Authentication

Every `/api/*` route requires **all three** headers. Possession of `X-API-Key` alone is not
sufficient — it is identity, not proof.

| Header | Required | Description |
| :--- | :--- | :--- |
| `X-API-Key` | yes | The plaintext key. Used **only** to look up the key record by SHA-256 of its value. |
| `X-Timestamp` | yes | Current UTC Unix time in **seconds**. Must be within ±300s of the server clock (`crypto::MAX_TIMESTAMP_SKEW_SECS`). |
| `X-Signature-256` | yes | `sha256=<hex>` — HMAC-SHA256 over the CANONICAL_V1 string below, keyed with the key's `signing_secret`. The `sha256=` prefix is **mandatory**; a bare hex digest is rejected. |

**CANONICAL_V1 signed string** — four fields joined by a single `\n` (LF), no trailing newline:

```
METHOD\nTARGET\nTIMESTAMP\nRAW_BODY
```

- `METHOD` is uppercase.
- `TARGET` is the full request target **including the query string** when present (e.g.
  `/api/ips?limit=10`). Read from `OriginalUri`, so it is the path the client sent, not the path
  relative to the `/api` mount point.
- `RAW_BODY` is the exact request body bytes; empty when there is no body.

**Anti-replay.** Two independent halves, both enforced:

1. **Freshness** — `|server_time - X-Timestamp| > 300` is rejected. The window is *symmetric*: a
   future-dated timestamp is as suspect as a stale one.
2. **Single use** — a `(key, signature)` pair already accepted inside that window is rejected.
   Consulted **after** the HMAC verifies.

> **Operational consequence.** A signature covers method, target, timestamp and body and nothing
> else, so **repeating a call unchanged within the same wall-clock second is indistinguishable from a
> replay** and is refused with `401`. Real clients never hit this — a retry lands on a later
> timestamp. A caller that genuinely needs the same request twice in one second must wait.

**Ordering.** Authenticate, then authorize: timestamp → key lookup → signature verification →
`bound_ips` CIDR check. A caller that cannot prove possession of the signing secret must never learn,
from a `403`-vs-`401` distinction, whether a guessed key is bound to its network.

### Signing helper

```bash
KEY="<PLAINTEXT_API_KEY>"
SECRET="<SIGNING_SECRET>"          # returned once by POST /api/keys or /rotate

# call METHOD PATH [JSON_BODY] — PATH excludes the host, includes the query string.
call() {
  local method="$1" path="$2" body="${3:-}"
  local ts; ts=$(date -u +%s)
  local sig; sig=$(printf '%s\n%s\n%s\n%s' "$method" "$path" "$ts" "$body" \
                   | openssl dgst -sha256 -hmac "$SECRET" | sed 's/^.*= //')
  curl -sS -X "$method" \
    -H "X-API-Key: $KEY" -H "X-Timestamp: $ts" -H "X-Signature-256: sha256=$sig" \
    ${body:+-H "Content-Type: application/json" -d "$body"} \
    "http://localhost:3000$path"
}
```

## 2. Error model

Every failure on every route returns the same envelope, defined once in `src/error.rs`:

```json
{ "error": "<human-readable message>" }
```

| Status | `AppError` variant | Raised when |
| :--- | :--- | :--- |
| `400 Bad Request` | `InvalidInput` | Malformed CIDR, bad URL, invalid enum value, unknown JSON field, malformed path/query segment |
| `401 Unauthorized` | `Unauthorized` | Missing/malformed/invalid auth header, stale or future timestamp, bad signature, replayed signature |
| `403 Forbidden` | `Forbidden` | Authenticated but lacking the required scope, verb, or ownership; client IP outside `bound_ips` |
| `404 Not Found` | `NotFound` | Resource absent — **or present but outside the caller's visibility scope** (see oracle discipline below) |
| `409 Conflict` | `Conflict` | Unique-name collision (e.g. duplicate group name) |
| `409 Conflict` | `ConflictWithDetails` | §6 pre-flight inventory: body carries `error` **plus** top-level `owned_entities` / `subtree_key_count` / `unresolved` |
| `413 Payload Too Large` | `BodyRejected` | Body exceeds `MAX_BODY_SIZE_MIB` (default **10 MiB**), applied router-wide including the static fallback |
| `500 Internal Server Error` | `DbError` | A genuine database failure — a query the driver rejected, a constraint the caller couldn't have known about. Detail is logged, never returned |
| `503 Service Unavailable` | `DbError` | The readiness probe (see [§4](#4-health--readiness-unauthenticated)) **or any authenticated route**, when the underlying `sea_orm::DbErr` is a transient lock/pool-contention failure — SQLite's `SQLITE_BUSY`/`SQLITE_LOCKED` (any extended-code variant, e.g. a stale-snapshot write conflict), Postgres's `lock_not_available`/`serialization_failure`/`deadlock_detected`, or the connection pool timing out. Body is `{"error": "Database busy or query timeout, please retry"}` — the request did nothing wrong, it lost a race, and a well-behaved caller should retry rather than treat it as a hard failure |
| `500 Internal Server Error` | `Internal` | Unreachable internal state |

**`500` vs `503` on a database error is decided once, centrally** (`src/error.rs`'s `is_transient_lock_error`), not per-handler — every route that touches `state.db` gets this distinction automatically. `busy_timeout` (10s by default; see `SCHEMA.MD`/`AGENT_NOTES.MD`) already makes SQLite *wait* for ordinary lock contention rather than fail immediately, so a `503` here means that wait was exhausted or the failure was the kind `busy_timeout` cannot absorb at all (a stale read snapshot under a `BEGIN DEFERRED` transaction, refused instantly regardless of the timeout).

**Oracle discipline (`RBAC_MODEL.md` §4).** An id outside the caller's visibility scope returns the
**identical status and body** a nonexistent id would — `404`, not `403`. This applies to keys,
webhooks, and webhook executions. It is a distinct control from the `401`-before-`403` ordering in
§1; both hold simultaneously.

Refusals that are a property of the **caller** rather than of the id (a missing global scope) are
correctly a uniform `403` for every id.

## 3. Conventions

- **`deny_unknown_fields`** is set on every request payload and query struct. A misspelled field or
  parameter is refused with `400` rather than silently ignored. The single exception is
  `ResolutionEntry`, which carries a `#[serde(flatten)]` field; its flattened `Resolution` enum
  denies unknown fields per variant instead.
- **Timestamps** in responses are naive UTC `NaiveDateTime`, serialized as
  `"2026-08-27T21:02:22.981830072"` (no timezone suffix).
- **Single-exposure secrets** — `plaintext_key`, `signing_secret`, and a webhook's `secret_token` are
  returned exactly once, by the endpoint that mints them. No read endpoint ever echoes them. A caller
  that loses one must rotate.
- **Group identifiers** — endpoints that accept a group take either `group_id` (UUID) or `group_name`
  (string), never both. `GroupPermInput.group_id` is a plain string, so passing a *name* in it also
  resolves.
- **Body size** — one router-wide ceiling, `MAX_BODY_SIZE_MIB` (default 10 MiB), applied outside the
  `/api` nest so it covers the static fallback too.

## 4. Health & readiness (unauthenticated)

The **only** routes outside `auth_middleware`. Mounted at the root, not under `/api`. They are held
to a rule the authenticated routes are not: they must disclose nothing an anonymous caller could not
already infer — no version string, no hostname, no row count, no database error text.

### `GET /health` · alias `GET /healthz`

**Handler:** `api::health_check` · **Auth:** none

Liveness. Touches nothing and cannot fail — the handler takes no `State`, so the compiler guarantees
a database outage cannot make it fail. An orchestrator uses this to decide whether to **restart** the
container.

| Status | Body |
| :--- | :--- |
| `200` | `{"status":"ok","service":"simply_ip_vault"}` |

### `GET /ready` · alias `GET /readyz`

**Handler:** `api::readiness_check` · **Auth:** none

Readiness. Checks that (1) the database answers a bounded single-id read — not `COUNT(*)`, which
would make every probe a table scan — and (2) the Master identity is pinned. A load balancer uses
this to decide whether to **route** to the container.

| Status | Body |
| :--- | :--- |
| `200` | `{"status":"ready","database":"up"}` |
| `503` | `{"status":"unavailable","database":"down"}` — database unreachable |
| `503` | `{"status":"unavailable","database":"up"}` — no Master pinned |

A failing probe never names which check failed and never carries the error; that goes to the
operator's log at `error` level. `503` rather than `500` is deliberate — nothing about the request
failed, the answer *is* "not ready".

## 5. Identity

### `GET /api/auth/me`

**Handler:** `api::get_me` · **Auth:** any authenticated key (no scope required)

Returns the presenting key's own identity, global scopes, and every per-group permission row it
holds. The dashboard calls this at boot to render the UI for the key's tier.

**Response `200`** — `MeResponse`:

```json
{
  "id": "uuid",
  "name": "string",
  "bound_ips": "127.0.0.1/32,::/0"  | null,
  "is_master": false,
  "can_manage_keys": false,
  "can_manage_webhooks": false,
  "can_create_groups": false,
  "group_permissions": [
    { "group_id": "uuid", "group_name": "fail2ban",
      "can_read": true, "can_write": true, "can_delete": false, "can_manage": false }
  ]
}
```

> Tier is *derived* by the client from these flags (`is_master` → Master, else `can_manage_keys` →
> Parent, else Daughter) rather than sent as its own field, so there is no second source of truth.

## 6. IP records

### `GET /api/ips`

**Handler:** `api::list_ips` · **Auth:** any authenticated key; results scoped to groups the caller
holds `can_read` on. Master sees everything.

**Query parameters** (`QueryFilters`, `deny_unknown_fields`):

| Name | Type | Req. | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `groups` | string (CSV) | no | — | Filter by group names, comma-separated (`fail2ban,sshd`) |
| `group_name` | string | no | — | Filter by a single group name; combines with `groups` (OR) |
| `group_id` | UUID | no | — | Filter by a single group id; combines with the above (OR) |
| `ip` | string | no | — | Substring match on `target_address`. A fully parseable address/CIDR is canonicalized first so it still matches the stored form |
| `cause` | string | no | — | Substring match on `cause` |
| `status` | string | no | — | `ban`\|`banlist` or `white`\|`whitelist`. Anything else → `400` |
| `max_age` | i64 (secs) | no | — | Only memberships whose `last_seen_at` is within this many seconds. Per membership, so it reads the observation in the group being listed |
| `since` | i64 (unix) | no | — | Delta-sync cutoff. In scope when this membership's `last_seen_at >= since`, **or** — with `include_deleted=true` — when `is_deleted` and `deleted_at >= since`. Scoped per membership: a change in one group never makes the same address look changed in another |
| `include_deleted` | bool | no | `false` | Include soft-deleted records. Scoped exactly as live ones; **not** master-gated |
| `limit` | u64 | no | `50` | Page size |
| `offset` | u64 | no | `0` | Page offset |
| `format` | string | no | — | `iplist` returns a flat address list instead of full records |
| `mode` | string | no | — | Synonym for `format` |
| `include_total` | bool | no | `false` | Wrap the response in a `{data, total, limit, offset, total_pages}` envelope instead of the bare array. Ignored under `format=iplist`/`mode=iplist` |

**Response `200`** — by default, an array of `IpRecordResponse`, ordered by `last_seen_at`
descending. Each item is one **membership**: an address's state within one group.

```json
[{
  "id": "uuid",            // the membership id
  "ip_record_id": "uuid",  // the canonical address row
  "target_address": "192.0.2.10", "group_name": "fail2ban",
  "group_type": "banlist", "cause": "SSH brute force" | null, "is_locked": false,
  "created_at": "...", "last_seen_at": "...",
  "is_deleted": false,
  "deleted_at": "...",        // omitted when null
  "deleted_by": "uuid-string" // MASTER ONLY — omitted for every other caller
}]
```

> There is no `updated_at`. `created_at` is when the address was first linked into this group, and
> `last_seen_at` is the latest observation in this group. `cause` is the most recent entry in the
> membership's append-only cause history, and is `null` when no cause was ever reported.

With `format=iplist` or `mode=iplist`, the shape is instead `{"ip_list": ["192.0.2.10", ...]}` —
sorted and de-duplicated, skipping the per-row group lookup.

With `include_total=true` (and no `format`/`mode=iplist`), the same array is returned under `data`,
alongside pagination metadata:

```json
{
  "data": [ /* IpRecordResponse[], identical shape and ordering to the bare-array response */ ],
  "total": 3214,
  "limit": 50,
  "offset": 0,
  "total_pages": 65
}
```

`total` counts every record matching all other filters (RBAC scoping included) across every page,
not just this one — it is a `COUNT(*)` over the same filtered query `data` is drawn from, taken
before `limit`/`offset` apply. `total_pages` is `ceil(total / limit)`, and is `0` (not `1`) when
`total` is `0` or `limit` is `0` — there is nothing to page through either way. `limit`/`offset`
echo the effective values used for this response (`50`/`0` when omitted from the request).

`total` and `data` are fetched inside one shared transaction, so a write landing between the two
queries cannot make them describe different snapshots of the table — `total` will never disagree
with what `data` itself implies across pages. The count query is a direct, unprojected
`SELECT COUNT(...)` (no subquery, no column materialization beyond the count) rather than a naive
`SELECT *`-wrapped count, but at the row counts this endpoint actually sees, latency is bounded by
how many rows match the caller's own filters — typically the groups one API key can read — not by
the size of the whole table; see `list_ips_include_total_count_scales_with_the_callers_own_rows_not_the_whole_table`
in `tests/schema_integrity_tests.rs` for measured figures.

> **Backward compatible by construction.** `include_total` is opt-in and defaults to `false`,
> so the root-array response every existing exporter/sync worker already parses is unchanged
> unless a caller asks for the envelope.
>
> **Naming a group the caller cannot read is not an error.** It contributes nothing, exactly as a
> nonexistent group would. Refusing would turn this endpoint into an existence oracle over group
> names (§4). A non-master with no readable groups at all gets `total: 0`/`total_pages: 0` under
> `include_total=true`, the same empty result the bare-array form returns as `[]`.
>
> `deleted_by` is withheld from non-masters even under `include_deleted`: §4 limits what one key may
> learn about another to id, name, and rights on a *shared* resource.

### `DELETE /api/ips` (soft or hard)

Soft-deletes one address's membership in one group. The hard form (`hard=true`) removes the row.
Both are identified by address and group, so the request never needs a database id.

**Auth:** `can_delete` on the named group. `hard=true` is **Master only**.

Parameters may arrive via **query string, JSON body, or both**. Query values win on overlap.

```http
DELETE /api/ips
Content-Type: application/json

{"target_address": "192.0.2.10", "group_name": "fail2ban"}
```

| Name | Type | Req. | Description |
| :--- | :--- | :--- | :--- |
| `target_address` | string | **yes** | Address or CIDR. Canonicalized before lookup |
| `group_id` | UUID | one of | Target group by id |
| `group_name` | string | one of | Target group by name |
| `hard` | bool | no | `false`. **Master only.** Removes the membership row; the address row too if no group still holds it |

Soft delete is the default: the membership is marked `is_deleted` with `deleted_at`/`deleted_by`
set, hidden from every read until a master restores it or retention purges it after 92 days.
Deleting an already-deleted membership returns `204` without moving `deleted_at`, so a repeat cannot
extend the retention window.

| Status | Meaning |
| :--- | :--- |
| `204` | Membership deleted (soft or hard) |
| `400` | `target_address` missing, or invalid JSON |
| `403` | No `can_delete` on the group; the membership is `is_locked`; or `hard=true` from a non-master |
| `404` | No such group, address, or membership in that group |

Enqueues an `IP_DELETE` webhook event after the transaction commits, for this group only.

> A delegated key never gets a hard delete: `can_delete` is a routine, widely-handed-out scope, and
> its blast radius should be a recoverable mistake rather than permanent data loss.

### `POST /api/ips/restore`

**Auth:** **Master only**. Identified by address and group, like `DELETE /api/ips`, as query, body, or both.

```http
POST /api/ips/restore
Content-Type: application/json

{"target_address": "192.0.2.10", "group_name": "fail2ban"}
```

Clears `is_deleted`, `deleted_at` and `deleted_by` on that membership, so it is indistinguishable
from one never deleted.

| Status | Body / meaning |
| :--- | :--- |
| `200` | `{"target_address":"...","group_name":"...","is_deleted":false,"restored":true}` |
| `400` | The membership is not deleted; nothing to restore |
| `403` | Caller is not master |
| `404` | No such group, address, or membership in that group |

> Master-only even though a delegated key may have caused the deletion: the point of the trash is
> that recovering from a compromised key does not depend on that same key's authority.

### `POST /api/system/purge-ips`

**Handler:** `api::purge_ip_records` · **Auth:** **Master only**. Irreversible.

Permanently drops soft-deleted records past the retention window — the same sweep the background
worker runs, exposed so an operator can reclaim space or honour a deletion request immediately.

**Request body** (`PurgeIpsPayload`, **optional** — an empty body uses the configured window):

| Field | Type | Req. | Description |
| :--- | :--- | :--- | :--- |
| `older_than_days` | i64 | no | Override the window for this sweep. Must be **> 0** |

**Response `200`:** `{"purged": 12, "retention_days": 92}`

> `0` is rejected rather than read as "purge everything": the difference between "empty the trash"
> and "empty the trash older than zero days" is one character, and the destructive reading must never
> be the one a typo selects.

### `POST /api/ban` · `POST /api/white`

**Handler:** `api::handle_ban` / `api::handle_white` (both → `handle_ip_upsert`) · **Auth:**
`can_write` on the target group. Creating a group that does not exist additionally requires
`can_create_groups`.

Registers an address into a banlist (`/ban`) or whitelist (`/white`) group. Re-registering an
existing address updates `last_seen_at` rather than failing, and **resurrects** a soft-deleted one.

**Request body** (`BanWhitePayload`):

| Field | Type | Req. | Description |
| :--- | :--- | :--- | :--- |
| `target_address` | string | **yes** | IPv4/IPv6 address or CIDR. Canonicalized: `1.2.3.4/32` → `1.2.3.4`; `192.168.1.50/24` → `192.168.1.0/24` |
| `group_id` | UUID | one of | Target group by id. **Never auto-created** |
| `group_name` | string | one of | Target group by name. Auto-created if absent and permitted |
| `cause` | string | no | Free-text reason |

| Status | Meaning |
| :--- | :--- |
| `200` | Registered |
| `400` | Invalid IP/CIDR; both or neither group identifier; **banning loopback/private/link-local**; group-type mismatch (`/white` into a banlist or vice versa) |
| `403` | No `can_write`; no access to the group; group absent and no `can_create_groups`; record `is_locked` |
| `404` | `group_id` supplied but no such group |

Enqueues an `IP_ADD` webhook event when the group **membership** is new, `IP_UPDATE` otherwise — keyed
on the membership, not the record row, so an address already banned in Group A that is added to
Group B is an `IP_ADD` from Group B's perspective.

> **Banlist address validation.** Loopback, unspecified, RFC 1918 / link-local IPv4, and
> link-local / unique-local IPv6 are refused for banlist targets — a rule covering `127.0.0.1` or
> `10.0.0.0/8` propagates to every downstream firewall and can cut a fleet off from itself.
> Whitelists are exempt by construction.

### `POST /api/records/batch`

**Handler:** `api::batch_records` · **Auth:** `can_write` on the group for `upsert`; `can_write`
**and** `can_delete` for `full_replace`.

Transactional bulk synchronisation, built for the companion exporter and sync worker. Everything runs
in one `Immediate` transaction: the per-record work, the `full_replace` sweep, and the audit row.

**Request body** (`BatchRecordsPayload`):

| Field | Type | Req. | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `group_name` | string | **yes** | — | Target group. Created if absent and permitted |
| `mode` | enum | no | `upsert` | `upsert` or `full_replace` |
| `records` | array | **yes** | — | Up to **10 000** entries (`MAX_BATCH_RECORDS`) |
| `skip_webhooks` | bool | no | `false` | Suppress **all** webhook dispatch for this batch |

Each `records[]` entry (`BatchRecordInput`):

| Field | Type | Req. | Description |
| :--- | :--- | :--- | :--- |
| `target_address` | string | **yes** | Canonicalized. Duplicates after canonicalization are **refused** |
| `cause` | string | no | Omitted leaves an existing value untouched; it does not clear it |
| `is_deleted` | bool | no | `false` on an existing deleted record restores it |
| `created_at` | datetime | no | Used **only** when the record is new; never overwrites an existing value |
| `last_seen_at` | datetime | no | Defaults to now. The observation time for this membership |
| `updated_at` | datetime | no | **Deprecated** alias for `last_seen_at`, kept for existing sync clients. Ignored when `last_seen_at` is present |
| `deleted_at` | datetime | no | Only meaningful alongside `is_deleted: true` |

**Response `200`** — `BatchRecordsResponse`:

```json
{ "created": 0, "updated": 0, "restored": 0,
  "locked_skipped": 0, "soft_deleted": 0, "linked": 0 }
```

| Status | Meaning |
| :--- | :--- |
| `400` | Batch over 10 000; invalid IP/CIDR; duplicate address after canonicalization; banlist address rule violated |
| `403` | No `can_write`; `full_replace` without `can_delete`; group absent and no `can_create_groups` |

**Webhook dispatch.** One event per record outcome — `IP_ADD` when the membership is new,
`IP_UPDATE` otherwise, and `IP_DELETE` for each record the `full_replace` sweep soft-deletes. Events
are buffered during the transaction and enqueued only **after** it commits. `skip_webhooks: true`
suppresses all of it; the record writes and the audit row are identical either way.

**What it will not do:** touch a locked record (counted in `locked_skipped`, exempt from the sweep);
hard-delete anything (`full_replace` soft-deletes); or bypass address validation.

## 7. API keys

### `POST /api/keys`

**Handler:** `api::create_api_key` · **Auth:** `is_master` **or** `can_manage_keys`

Every key created here is a **Daughter** by construction — the created key's `parent_key_id` is set to
the caller.

**Request body** (`CreateApiKeyPayload`):

| Field | Type | Req. | Description |
| :--- | :--- | :--- | :--- |
| `name` | string | **yes** | Human-readable name |
| `bound_ips` | string | no | Comma-separated CIDRs (`127.0.0.1/32,10.0.0.0/8,::/0`). Each is validated |
| `can_manage_keys` | bool | no | **Master-grantable only** (R4) |
| `can_manage_webhooks` | bool | no | **Master-grantable only** (R4) |
| `can_create_groups` | bool | no | **Master-grantable only** (R4) |

> **`is_master` is not a field on this type**, and `deny_unknown_fields` is what makes that absence
> mean something: a payload naming it is refused by *deserialization* with `400`, before any handler
> runs. `RBAC_MODEL.md` §5 requires exactly this — "rejecting it at the handler is not sufficient,
> since a later handler can reintroduce the path."

**Response `200`** — `CreateApiKeyResponse`. **Both secrets are shown exactly once:**

```json
{ "id": "uuid", "plaintext_key": "64-hex", "signing_secret": "64-hex",
  "name": "worker", "bound_ips": "0.0.0.0/0,::/0" | null }
```

| Status | Meaning |
| :--- | :--- |
| `400` | Invalid CIDR; unknown field (including `is_master`) |
| `403` | Neither master nor `can_manage_keys`; or a non-master requested a master-only scope |

### `GET /api/keys`

**Handler:** `api::list_api_keys` · **Auth:** `is_master` **or** `can_manage_keys`

Implements §4's three visibility scopes in one listing:

| Caller | Sees |
| :--- | :--- |
| Master | every key, `"full"` |
| `can_manage_keys` holder | its own `parent_key_id` subtree `"full"`, plus every key sharing a group it **manages** (R2 conjunction), `"minimal"` |
| anyone else | `403` |

**Response `200`** — array of `ApiKeySummary`. The `view` field says which shape each entry is:

```json
// view: "full"
{ "id": "uuid", "name": "worker", "view": "full", "prefix": "a1b2c3d4",
  "bound_ips": null, "is_master": false, "can_manage_keys": false,
  "can_manage_webhooks": false, "can_create_groups": false,
  "parent_key_id": "uuid" | null, "created_at": "...",
  "group_permissions": [ /* ALL rows */ ] }

// view: "minimal" — every full-only field is ABSENT, not false
{ "id": "uuid", "name": "other-tenant", "view": "minimal",
  "group_permissions": [ /* only rows on groups the CALLER manages */ ] }
```

> **An absent field in the minimal shape means *withheld*, not `false`.** A client that renders a
> missing `can_manage_keys` as unprivileged is asserting the absence of scopes it was never shown.
> Read `view`, not field presence. `key_hash` and `signing_secret` appear in neither shape.

### `PUT /api/keys/{id}`

**Handler:** `api::update_api_key` · **Auth:** `is_master` or `can_manage_keys`, **and** the target
must be inside the caller's own subtree (`404` otherwise)

**Request body** (`UpdateApiKeyPayload`) — every field optional; **omitted means unchanged**:

| Field | Type | Description |
| :--- | :--- | :--- |
| `name` | string | New name |
| `bound_ips` | string | New comma-separated CIDRs; each validated |
| `can_manage_keys` | bool | Master-grantable only; `false` (revocation) is permitted from anyone who may edit the key |
| `can_manage_webhooks` | bool | Same |
| `can_create_groups` | bool | Same |

**Response `200`:** the updated key as a `"full"` `ApiKeySummary`.

| Status | Meaning |
| :--- | :--- |
| `400` | Invalid CIDR; unknown field (including `is_master`) |
| `403` | Missing scope; a non-master granting a master-only scope; **any edit to the Master key other than its own `bound_ips`, by itself** |
| `404` | No such key, or outside the caller's subtree |

> **Revocation is not elevation.** `Some(false)` over a currently-true scope is always permitted;
> only `Some(true)` over a currently-false one is gated. This is load-bearing for the dashboard,
> which omits master-only fields entirely rather than posting them as `false` — otherwise a Parent
> renaming a Daughter would silently revoke scopes a Master had granted.
>
> **The Master key is immutable through the API except for its own `bound_ips`,** which it alone may
> edit. A payload mixing `bound_ips` with any other field is refused whole rather than partially
> applied.

### `DELETE /api/keys/{id}`

**Handler:** `api::delete_api_key` · **Auth:** `is_master` or `can_manage_keys`, target inside the
caller's subtree

Deletes the target **and its entire `parent_key_id` subtree**, gated on §6's pre-flight inventory.
`api_key_group_permissions` rows follow by foreign key; **no resource table does**.

**Request body** (`DeleteKeyPayload`) — **optional**; an empty body means "no resolutions":

```json
{ "resolutions": [
    { "entity_type": "group",   "id": "uuid", "action": "delete" },
    { "entity_type": "webhook", "id": "uuid", "action": "reassign",
      "owner_key_id": "uuid" }
] }
```

`entity_type` is `"group"` or `"webhook"`; `action` is `"delete"` or `"reassign"`.

| Status | Meaning |
| :--- | :--- |
| `204` | Deleted |
| `400` | Duplicate resolution; a resolution naming an entity not in the inventory; reassignment to a key **inside the doomed subtree** |
| `403` | Missing scope; deleting yourself; deleting the Master key |
| `404` | No such key, or outside the caller's subtree |
| `409` | Owned entities need resolution — body carries the inventory (below), or `unresolved` for a partial map |
| `409` | A `parent_key_id` cycle puts the caller inside the subtree being deleted |

**`409` inventory body:**

```json
{ "error": "Refusing to delete 'name' (abc12345...): 2 entities in its subtree need ...",
  "subtree_key_count": 3,
  "owned_entities": [
    { "entity_type": "group", "id": "uuid", "name": "fail2ban",
      "owner_key_id": "uuid", "owner_name": "worker" }
  ] }
```

> **Every validation runs before the first write.** A partial map that applied the resolutions it
> *did* carry before discovering the gap would destroy data the caller never decided about, so a
> refusal leaves the installation byte-identical.
>
> **Reassigning into the doomed subtree is refused.** It reads as a rescue and is a deferred
> orphaning: the new owner disappears microseconds later.

### `POST /api/keys/{id}/rotate`

**Handler:** `api::rotate_api_key` · **Auth:** `is_master` or `can_manage_keys`, target inside the
caller's subtree

Replaces **both** credentials — the API key and its signing secret. The old `key_hash` is overwritten,
so the previous credential stops working immediately. Also the recovery path for keys created before
`signing_secret` existed.

**Response `200`** — `RotateKeyResponse`, **both values shown once**:

```json
{ "id": "uuid", "plaintext_key": "64-hex", "signing_secret": "64-hex" }
```

| Status | Meaning |
| :--- | :--- |
| `403` | Missing scope; **rotating the Master key is refused for every caller, master included** |
| `404` | No such key, or outside the caller's subtree |

> Rotation returns a working credential in its response body, so an API-reachable master rotation
> would be an API-reachable way to *mint* a master credential from any session that already holds
> one. Re-minting the master is instead: delete the row directly in the database; the service
> re-mints at next boot.

### `POST /api/keys/{id}/rotate-secret`

**Handler:** `api::rotate_signing_secret` · **Auth:** same as `/rotate`

The narrow sibling: replaces **only** the HMAC signing secret. The key's id, name, `key_hash` /
`X-API-Key`, `bound_ips`, global scopes and every group grant are left untouched — the right tool for
routine hygiene, and the documented recovery path for a key whose `signing_secret` is `NULL`.

**Response `200`** — `RotateSigningSecretResponse`:

```json
{ "id": "uuid", "name": "worker", "signing_secret": "64-hex" }
```

Same status codes as `/rotate`. The previous secret stops working the instant this returns.

### `POST /api/keys/{id}/groups` · alias `POST /api/keys/{id}/permissions`

**Handler:** `api::update_key_group_permissions` · **Auth:** R2 conjunction — global
`can_manage_keys` **and** `can_manage = true` on the caller's own row for the target group. Master
bypasses.

Creates or updates one key's permission row on one group. Both paths are the same handler; the
`/permissions` spelling matches the revoke route below, and `/groups` is kept for compatibility.

**Request body** (`GroupPermInput`):

| Field | Type | Req. | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `group_id` | string | one of | — | Group by id **or name** (plain string, not a strict UUID) |
| `group_name` | string | one of | — | Group by name. May be auto-created if permitted |
| `can_read` | bool | **yes** | — | |
| `can_write` | bool | **yes** | — | Requires `can_read` |
| `can_delete` | bool | **yes** | — | Requires `can_read` |
| `can_manage` | bool | no | `false` | Administer this group's permission rows |

| Status | Meaning |
| :--- | :--- |
| `200` | Row created or updated |
| `400` | `can_write`/`can_delete` without `can_read`; both/neither group identifier; **target is a master key** |
| `403` | R2 conjunction unmet; a grant exceeding the caller's own verbs (R1/R7); group absent and no `can_create_groups` |
| `404` | Target key not found; or `group_id` unresolvable (identifiers are never auto-created) |

> **Classification is by effect, not by route (R6).** A payload that adds any verb the target lacks —
> or creates the row at all — is a **grant**, and gets R2 **plus** the per-verb R1 ceiling. A payload
> that only lowers an existing row is a **revocation** reached through the general endpoint, and gets
> R2 alone: no proof over the verb removed, and self-targeting permitted.
>
> Auto-creating a group via `group_name` provisions **no** permission row for the creator, so a
> non-master arriving that way holds no `can_manage` and is refused by R2. Only a master can open a
> brand-new group for delegation.

### `DELETE /api/keys/{id}/permissions/{group_identifier}`

**Handler:** `api::revoke_key_group_permission` · **Auth:** R2 conjunction (Master bypasses)

Removes one key's permission row for one group. `{group_identifier}` may be the group's **UUID or its
name**.

| Status | Meaning |
| :--- | :--- |
| `204` | Row removed |
| `403` | R2 conjunction unmet |
| `404` | No such group; **or no such grant** (checked before the authority test, so a nonexistent grant never becomes a `403` confirming the group exists) |

> Revocation requires **no** proof over the verb removed, and **self-revocation is permitted** (R6).
> Removing a verb raises nobody's authority. The counterpart safeguard is that a master's view never
> depends on a permission row, so a group whose last manager revokes itself stays listable and
> re-grantable.

## 8. IP groups

All four group routes carry an `/ip_groups` alias registered inside the same authenticated nest, for
companion agents that spell it that way. The alias is byte-identical in behavior — same handler, same
auth.

### `GET /api/groups` · alias `GET /api/ip_groups`

**Handler:** `api::list_ip_groups` · **Auth:** **any authenticated key** — no `is_master` or
`can_manage_keys` gate

| Caller | Sees |
| :--- | :--- |
| Master | every group |
| Any other key | only groups where it holds `can_read` **or** `can_write` **or** `can_delete` **or** `can_manage` |
| A key with no permission rows | `200` with `[]` — **never `403`** |

**Response `200`** — array of `ip_group::Model`:

```json
[{ "id": "uuid", "name": "fail2ban", "group_type": "banlist",
   "description": null, "owner_key_id": "uuid" | null, "created_at": "..." }]
```

> The `can_manage` arm is load-bearing: the least-privilege rule only forces `can_read` for
> `can_write`/`can_delete`, so a `can_manage`-only row (`can_read: false`) is reachable through the
> grant API — and such a key must be able to list the group it administers.
>
> Master branches on `is_master` **before** consulting the permission table, so a group whose last
> manager revoked itself (leaving it with no rows at all) stays listable.

### `POST /api/groups` · alias `POST /api/ip_groups`

**Handler:** `api::create_ip_group` · **Auth:** `is_master` **or** `can_create_groups`

**Request body** (`CreateIpGroupPayload`):

| Field | Type | Req. | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `name` | string | **yes** | — | Unique across the installation |
| `group_type` | string | no | `banlist` | `whitelist`, or **anything else → `banlist`**. Never rejected over this field |

**Response `200`:** `{"id":"uuid","name":"fail2ban","group_type":"banlist"}`

| Status | Meaning |
| :--- | :--- |
| `403` | Neither master nor `can_create_groups` |
| `409` | A group with that name already exists |

**Auto-provisioning.** A non-master creator is granted `can_read`/`can_write`/`can_delete` on the new
group — and **not** `can_manage`. Creating a resource does not mint the row R2 requires, so a Parent
that creates a group can use it but cannot delegate access until a Master grants `can_manage`.
`owner_key_id` is set to the creator (`null` when a master creates it, since `null` already means
master-only).

### `DELETE /api/groups/{id}` · alias `DELETE /api/ip_groups/{id}`

**Handler:** `api::delete_ip_group` · **Auth:** **§3 lifecycle** — Master **or** the group's
`owner_key_id`, and nobody else

| Status | Meaning |
| :--- | :--- |
| `204` | Deleted (cascades to memberships, permission rows, and webhooks on this group) |
| `403` | Neither master nor owner |
| `404` | No such group |

> Holding `can_manage` on the group's permission rows, or any read/write/delete verb over its
> contents, confers **no** lifecycle authority. An unowned group (`owner_key_id: null` — every
> pre-migration row, and everything a master creates) is master-only.

### `PUT /api/groups/{id}/owner` · alias `PUT /api/ip_groups/{id}/owner`

**Handler:** `api::reassign_group_owner` · **Auth:** **Master only**

**Request body** (`ReassignOwnerPayload`): `{"owner_key_id": "uuid" | null}` — `null` clears
ownership, returning the group to master-only lifecycle authority.

**Response `200`:** `{"id":"uuid","owner_key_id":"uuid" | null}`

| Status | Meaning |
| :--- | :--- |
| `400` | No such key to assign; **or the target is the master key** (`null` already means master-only, and two spellings of one state invite guards that check the wrong one) |
| `403` | Caller is not master |
| `404` | No such group |

> Deliberately not delegable to the current owner: ownership is the authority to *destroy* the
> resource, so a transferable owner flag would let a tenant pass that authority onward without the
> master who granted it seeing the transfer. This is also the sole recovery path for the `NULL`
> ownership backfill.

## 9. Webhooks

A webhook is a **creator-private entity** (§4): visible exclusively to its `owner_key_id` and Master,
and **never** exposed by the shared-resource rule. Every endpoint below shares one base gate —
`is_master || can_manage_webhooks` — and then narrows to ownership, answering **`404`** (not `403`)
for a webhook the caller does not own.

### `POST /api/webhooks`

**Handler:** `api::create_webhook` · **Auth:** base gate **plus** `can_read` on the target group

**Request body** (`CreateWebhookPayload`):

| Field | Type | Req. | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `name` | string | **yes** | — | |
| `target_url` | string | **yes** | — | `http`/`https`, must have a host. Supports `$variable` substitution |
| `group_id` | UUID | **yes** | — | Monitored group |
| `payload_template` | string | **yes** | — | Body template with `$variable` substitution |
| `secret_token` | string | cond. | `""` | **Required** by `CANONICAL_V1` and `HMAC_ONLY` |
| `auth_mode` | string | no | `CANONICAL_V1` | `CANONICAL_V1`, `HMAC_ONLY`, `API_KEY_ONLY`, `NONE`. `BODY_ONLY` accepted as a legacy alias for `HMAC_ONLY` |
| `signature_mode` | string | no | — | Deprecated alias for `auth_mode`; ignored when both are present |
| `api_key` | string | cond. | — | Sent as `X-API-Key`. **Required** by `API_KEY_ONLY`. Blank normalizes to unset |
| `hmac_template` | string | no | `{method}\n{path}\n{timestamp}\n{body}` | `CANONICAL_V1` only. **Must contain `{body}`** |
| `signature_header` | string | no | `X-Signature-256` | Blank normalizes to the default |
| `signature_prefix` | string | no | `sha256=` | An explicit `""` sends a bare digest — meaningful, not unset |
| `headers_json` | string | no | — | JSON object of custom headers |
| `events` | string (CSV) | no | all | Subset of `IP_ADD`,`IP_UPDATE`,`IP_DELETE` |
| `is_active` | bool | no | `true` | |

**Response `200`:** `{"id":"uuid","target_url":"...","auth_mode":"CANONICAL_V1"}`

| Status | Meaning |
| :--- | :--- |
| `400` | Malformed URL, non-http(s) scheme, missing host; unknown `events` token; unrecognized `auth_mode`; **signing mode without `secret_token`**; **`API_KEY_ONLY` without `api_key`**; **`hmac_template` missing `{body}`** |
| `403` | Base gate unmet, or no `can_read` on the target group |

> **Per-mode preconditions are enforced at creation, not at dispatch.** Deferring them to the
> background worker would surface a misconfiguration only as a log line, on every future event.
> `{body}` is mandatory because a signature that does not cover the payload is replayable across
> payloads.

#### Auth modes

| `auth_mode` | Signed message | Headers dispatched | Requires |
| :--- | :--- | :--- | :--- |
| `CANONICAL_V1` *(default)* | the resolved `hmac_template` | signature + `X-Timestamp`, plus `X-API-Key` when set | `secret_token` |
| `HMAC_ONLY` | `RAW_BODY` | the signature **and nothing else** — no `X-API-Key` even when set, no `X-Timestamp` | `secret_token` |
| `API_KEY_ONLY` | *(none)* | `X-API-Key` | `api_key` |
| `NONE` | *(none)* | *(none)* | — |

#### Template variables

`target_url` and `payload_template` share one evaluator: `$target_address`/`$ip`, `$action`/`$event`,
`$cause`, `$group_name`/`$group_id`, `$timestamp`. Single left-to-right pass with **no rescanning** —
`cause` is caller-controlled, so a value containing another placeholder must not be expanded twice.

`hmac_template` uses `{method}`, `{path}`, `{timestamp}`, `{body}` with `\n`/`\r`/`\t`/`\\` escapes.
A literal path written into the template overrides the `{path}` derived from `target_url`, which is
what makes a receiver behind a path-rewriting proxy verifiable.

### `GET /api/webhooks`

**Handler:** `api::list_webhooks` · **Auth:** base gate; non-master filtered to `owner_key_id = caller`

**Response `200`** — array of `WebhookSummary`:

```json
[{ "id": "uuid", "name": "alerts", "target_url": "https://...",
   "headers_json": null, "payload_template": "{...}", "group_id": "uuid",
   "is_active": true, "events": "IP_ADD,IP_DELETE" | null,
   "auth_mode": "CANONICAL_V1",
   "hmac_template": "{method}\\n{path}\\n{timestamp}\\n{body}",
   "has_api_key": false,
   "signature_header": "X-Signature-256", "signature_prefix": "sha256=",
   "created_at": "..." }]
```

> **Neither `secret_token` nor `api_key` is ever returned.** Both are caller-supplied plaintext
> credentials for a *remote* system: leaking `secret_token` would let any reader forge valid
> signatures, and leaking `api_key` would hand over a working credential on the receiving system.
> The listing reports `has_api_key: bool` instead. `hmac_template`, `signature_header` and
> `signature_prefix` **are** returned, resolved to their effective values — they carry structure, not
> key material.
>
> Pre-migration rows carry `owner_key_id = NULL` and are visible to nobody but the master until
> reassigned.

### `PUT /api/webhooks/{id}`

**Handler:** `api::update_webhook` · **Auth:** base gate + ownership (`404` otherwise). Retargeting to
a new group additionally requires `can_read` on it.

Every stored field is editable. **All fields optional; omitted means unchanged.** Accepts the same
field set as `CreateWebhookPayload` minus `signature_mode`, plus `group_id`.

**Response `200`** — `UpdateWebhookResponse`: the full `WebhookSummary` flattened, plus:

```json
{ "...WebhookSummary fields...",
  "secret_rotated": true,
  "secret_token": "64-hex"   // present ONLY when rotated AND not caller-supplied
}
```

| Status | Meaning |
| :--- | :--- |
| `400` | Same validation set as create; plus `API_KEY_ONLY` without an effective `api_key` |
| `403` | Base gate unmet; no `can_read` on a new target group; **privileged-webhook gate** (below) |
| `404` | No such webhook, or not owned by the caller |

> **Repointing invalidates the secret.** If `target_url`, `hmac_template`, or `auth_mode` changes into
> a signing mode, `secret_token` is replaced — with the caller's own value if supplied, otherwise a
> fresh one returned once here. Without forced rotation, an editor could point the webhook at a
> server it controls and simply *wait*: the next dispatch would arrive carrying a valid signature
> over an attacker-chosen payload — a working forgery oracle for the receiver's shared secret.
>
> **The privileged-webhook gate.** On a webhook that already carries a non-empty `api_key`, changing
> `target_url`, `hmac_template`, `auth_mode`, or `api_key` is **master-only**. None of those changes
> is undone by rotating `secret_token`, because the `api_key` belongs to the remote system and is
> never rotated here. Every other field — name, group, payload template, events, signature
> header/prefix, active state — stays editable by any owner.

### `DELETE /api/webhooks/{id}`

**Handler:** `api::delete_webhook` · **Auth:** base gate + ownership

| Status | Meaning |
| :--- | :--- |
| `204` | Deleted — **cascades to this webhook's entire `webhook_executions` history** |
| `403` | Base gate unmet |
| `404` | No such webhook, or not owned by the caller |

### `PUT /api/webhooks/{id}/owner`

**Handler:** `api::reassign_webhook_owner` · **Auth:** **Master only**

Body and semantics identical to `PUT /api/groups/{id}/owner`.

**Response `200`:** `{"id":"uuid","owner_key_id":"uuid" | null}`

### `POST /api/webhooks/{id}/test`

**Handler:** `api::test_webhook` · **Auth:** base gate + ownership

Fires a live, synchronous dispatch through the same `prepare_dispatch` path a real event uses, so the
test exercises the exact bytes a real dispatch would send. No request body.

The event is synthetic and fixed — address `127.0.0.1/32`, action `TEST` — and **bypasses the
webhook's own `events` filter**, since an explicit human-triggered test must run regardless of what
live traffic the webhook subscribes to.

**Response `200`** — `WebhookTestResult`:

```json
{ "success": true, "status": 200,
  "headers": { "content-type": "application/json" } | null,
  "body": "truncated response snippet" | null,
  "error": null,                      // non-null exactly when success is false
  "blocked_by_ssrf_filter": false }
```

Note `200` is returned even for a *failed* delivery — the request succeeded, the result describes the
delivery. Logs a `webhook_executions` row with `event_type = "TEST"`; never retried.

| Status | Meaning |
| :--- | :--- |
| `403` | Base gate unmet |
| `404` | No such webhook, or not owned by the caller |

### `POST /api/webhooks/{id}/clone`

**Handler:** `api::clone_webhook` · **Auth:** base gate + ownership of the **source** + `can_read` on
the source's group. **Master-only when the source is privileged** (carries a non-empty `api_key`).

Duplicates an existing webhook's configuration under a new name.

**Request body** (`CloneWebhookPayload`): `{"name": "New Webhook Name"}`

**Response `201 Created`** — `CloneWebhookResponse`: the new `WebhookSummary` flattened, plus:

```json
{ "...WebhookSummary fields...",
  "secret_token": "64-hex"   // present ONLY when the auth mode requires a secret
}
```

**Duplicated:** `target_url`, `group_id`, `auth_mode`, `signature_header`, `signature_prefix`,
`hmac_template`, `payload_template`, `headers_json`, `events`, `is_active`, `api_key`.

**Not duplicated:**

- `owner_key_id` — set to the **caller**, not the source's owner. The caller is the one asking for a
  new dispatch target to exist.
- `secret_token` — **never** copied. Two webhooks sharing one HMAC secret means a receiver able to
  verify one dispatch can verify the other, and a compromise of either exposes both. A fresh secret
  is generated whenever the auth mode requires one, returned exactly once.

| Status | Meaning |
| :--- | :--- |
| `403` | Base gate unmet; no `can_read` on the source's group; **non-master cloning a privileged webhook** |
| `404` | No such webhook, or not owned by the caller |

> The privileged gate applies **even to the source webhook's own non-master owner**: cloning fans a
> receiver-trusted credential out to a *second*, independently-editable dispatch target, a strictly
> larger exposure than editing the original in place.

## 10. Webhook executions

One row per outbound HTTP **attempt**, including retries — a delivery that failed twice before
succeeding leaves three rows.

**Retention, not permanence.** Successful rows are purged after 24h, failed rows after 7 days
(`WEBHOOK_EXECUTION_RETENTION_SUCCESS_HOURS` / `..._FAILURE_HOURS`). The asymmetry is deliberate: a
failure is what an operator comes back to investigate; a confirmed success is not.

### `GET /api/webhooks/executions`

**Handler:** `api::list_webhook_executions` · **Auth:** base gate, then narrowed to executions whose
`webhook_id` resolves to a webhook the caller **owns**. `can_manage_keys` satisfies neither half.

**Query parameters** (`WebhookExecutionQuery`, `deny_unknown_fields`). Every filter is `AND`-combined
with every other **and** with the ownership scoping, so no filter can widen what a non-master sees.

| Name | Type | Req. | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `webhook_id` | UUID | no | — | Narrow to one webhook's history |
| `event_type` | string | no | — | Exact match: `IP_ADD`, `IP_UPDATE`, `IP_DELETE`, `TEST` |
| `is_success` | bool | no | — | Superseded by `status` when both are given |
| `status` | string | no | — | `success`, `failed`\|`failure`\|`error`, or a bare HTTP code (`"503"`) matching `status_code` exactly |
| `search` | string | no | — | Free text across the owning webhook's **name**, the event's **address**, and its **cause** — matches any one (`OR`) |
| `group_id` | UUID | no | — | Via the webhook's **current** `group_id`, not its value at dispatch time |
| `ip` | string | no | — | Substring on `target_address`, canonicalized like `GET /api/ips`'s `ip` filter |
| `from_date` | i64 (unix) | no | — | Inclusive lower bound on `created_at` |
| `to_date` | i64 (unix) | no | — | Inclusive upper bound on `created_at` |
| `limit` | u64 | no | `50` | |
| `offset` | u64 | no | `0` | |

**Response `200`** — array of `webhook_execution::Model`, ordered by `created_at` descending:

```json
[{ "id": "uuid", "webhook_id": "uuid", "event_type": "IP_ADD",
   "status_code": 200 | null, "is_success": true, "duration_ms": 42,
```

## Appendix B — RBAC vocabulary

**Three tiers**, and the boundary between the lower two is one flag:

| Tier | Determined by | May manage resources |
| :--- | :--- | :--- |
| **Master** | `is_master` — exactly one exists, pinned at boot | everywhere; bypasses all checks |
| **Parent** | `can_manage_keys == true` | where a `can_manage` row is held |
| **Daughter** | `can_manage_keys == false` | never |

**Global scopes** — all three are **Master-granted only** (R4): `can_manage_keys`,
`can_manage_webhooks`, `can_create_groups`.

**Per-group verbs** (`api_key_group_permissions`): `can_read`, `can_write`, `can_delete`,
`can_manage`. `can_write`/`can_delete` require `can_read`.

**R2 — manage is a conjunction.** Touching *any* key's permission rows on a group requires **both**
global `can_manage_keys` **and** `can_manage = true` on the caller's own row for that group.

| Caller holds | Grant / widen | Revoke / reduce |
| :--- | :--- | :--- |
| `can_manage_keys` only | ❌ | ❌ |
| `can_manage` on the group only | ❌ | ❌ |
| **Both** | ✅, bounded per verb (R1/R7) | ✅, no proof over the verb removed (R6) |
| `is_master` | ✅ | ✅ |

**Ownership vs. management.** `can_manage` is authority over a resource's **permission rows**;
`owner_key_id` is authority over its **existence** (§3). Conflating them means the key trusted to
hand out read access can also delete the thing everyone is reading.

**Lineage confers nothing (R3).** `parent_key_id` exists solely for cascade deletion and visibility
scoping. No permission guard reads it; a daughter of the Master is an ordinary daughter key.
